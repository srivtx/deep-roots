module 03 · the four families and the machinery that finds them

The bug from first principles

chapter 01 · ~14 min read · deep-roots learning program
The 30-second version. A bug is a divergence between the behavior you intended and the behavior the program delivers, and the intended half is mostly unwritten, so "it works as coded" is not a defense. Executions double with every branch while tests grow linearly, so every suite is a thin slice of an exponential space, and the slice misses corners, where the four failure families live — each a mechanism, not a symptom. Timing, allocator layout, and optimization level are invisible inputs: hence Heisenbugs and "works on my machine." Fault, error, failure, and Boehm's 1:10:100 curve close the argument.

1. The definition: a divergence, and half the spec is unwritten

Every bug report is secretly about two programs: the one you meant to write and the one that exists.

  • The spec: the input → behavior mappings you intend. For "print the file, sorted" it includes clauses no ticket ever wrote: never lose the file, never hang, 10 GiB files too.
  • The behavior: the mappings the program implements — every path you never executed, every environment you never ran it in.

A bug is any input (or input + environment) on which these two sets disagree. Three consequences:

  1. The bug exists whether or not anyone observed it. Divergence is a property of the program plus environment, not of the bug report. Code that ran in production for a decade is not verified, merely un-activated (section 5: a dormant fault).
  2. "It works as coded" is a category error. Code approximates intent; the bug is the gap. "Bug or feature?" asks what the spec says; where it is silent, the answer is a product decision that, once written, makes the divergence measurable.
  3. A crash is not the bug. A crash is one observable, usually the kindest: loud and immediate. The dangerous bugs diverge silently, and the failure surfaces far away and much later.

2. Why bugs cluster: paths grow exponentially, tests grow linearly

Take the smallest interesting case, a C function with five independent two-way branches:

/* discount.c — five independent decisions, each doubling the path count */
int discount(int age, int vet, int student, int coupon, int member) {
    int d = 0;
    if (age > 64)  d += 10;   /* branch 1: 2 outcomes */
    if (vet)       d += 10;   /* branch 2: 2 outcomes */
    if (student)   d += 5;    /* branch 3: 2 outcomes */
    if (coupon)    d += 5;    /* branch 4: 2 outcomes */
    if (member)    d += 5;    /* branch 5: 2 outcomes */
    return d;
}

Each branch doubles the routes one call can take: five branches give 2^5 = 32 paths, and any test walks exactly one of them. "All true" and "all false" execute every line and every branch both ways, yet touch 2 of 32:

   the 32 paths of discount(), one cell each (rows = bits b4b3, cols = b2b1b0)

   | . | . | . | . | . | . | . | . |   100% branch coverage,
   | . | . | . | . | . | . | . | . |   2/32 = 6.25% path coverage.

One 32-branch function costs 49.7 days to path-cover; a real module has hundreds. Inputs are not booleans either: one 32-bit argument is 2^32 points per path. Loops multiply further: B branches iterated n times yield up to (2^B)^n traces. Threads: two threads of 6 atomic blocks each admit C(12,6) = 924 interleavings; as one loop iteration run 3 times, 924^3 ≈ 7.9 × 10^8.

The other side of the ledger is linear: minutes per test, a CI budget in hours. Every test suite is a thin, linear slice of an exponential space, and bugs cluster where the slice is thinnest: boundaries between path regions (off-by-ones), branch combinations (each branch tested alone, the pair never co-executed), rare interleavings. "Corner case" folklore is this arithmetic.

3. The four families: classify by mechanism, not symptom

Symptoms (crash, hang, wrong number, lost data) are many-to-one: every family can produce every symptom, so symptom triage tells you nothing. Classify by mechanism, the root cause in the execution machinery. Module 01's arc yields exactly four ways the model in the code can diverge from the model in the head:

FamilyDefining property (mechanism)Canonical shapesDetector (→ ch05)
MemoryAccesses bytes the program does not own: out of bounds, out of lifetime, or misinterpreted.Overflow, use-after-free, double-free, uninitialized read.ASan
ConcurrencyThe outcome depends on an interleaving no line of code specifies.Data race, TOCTOU, deadlock, lost wakeup.TSan

One root fact each. Memory: in C/C++ a pointer is a raw number and nothing checks at runtime which bytes it may name — module 01 ch21's four primitives, which is why ~70% of severe CVEs at Microsoft and Chromium (2019) are memory-safety bugs. Concurrency: each thread's code is sequentially correct; the bug lives between threads. Numeric: the mathematical value and its machine encoding are different objects, and the conversion is silent. State: every step is locally legal; the forbidden sequence is nobody's line of code. Mechanism also predicts visibility: memory faults are deterministic given a layout; concurrency faults need a rare interleaving to fire — the next section.

4. Heisenbugs and "works on my machine": the invisible inputs

The inputs you list in a test: argv, files, network. The inputs your program also reads, unlisted: thread schedule, allocator state, code layout, optimization level, core count, ASLR base, locale, timezone. The spec never pins them, so divergences keyed to them are bugs by section 1's definition.

A Heisenbug is a failure whose probability is dominated by invisible inputs, which is why observing it changes it: attach gdb and every thread stops (schedule changed); add a printf and you allocate a buffer and take a lock (allocator state and timing changed). The bug appears to flee the instrument (1980s folklore; its opposite, the always-reproducing bug, is a Bohrbug).

"Works on my machine" is the same statement in memory-model terms. The program is really (source + toolchain + allocator + scheduler); change the machine and the memory model changes, and it decides which failures you get. The chain comes from module 01 ch19: glibc's tcache is a per-thread LIFO cache (bins of 7 chunks), so one extra allocation anywhere (a locale switch, one more printf) changes which chunk your dangling pointer aliases. On glibc ≥ 2.29 (verified on 2.41), a tcache free clobbers only the first 16 user bytes (next + key), so a use-after-free at offset 16+ reads old, plausible data and passes; under ASan the same access hits a poisoned redzone and aborts. Same source, different heap: silent wrong answer on one machine, crash on the other.

The compiler plays the same trick. In See it yourself, a two-thread counter with a data race loses about half its updates at -O0 and prints the correct total at -O2, because gcc 14.2 legally collapsed the loop into one addq — a data race is undefined behavior in C11 (§5.1.2.4), so the optimizer owes it nothing (module 10 ch02). "Cannot reproduce" is a fact about your reproduction, not about the fault. Match the invisible inputs, not "same OS."

5. Fault, error, failure — and the price of finding out late

The dependability community (Avizienis, Laprie, Randell, Landwehr, "Basic Concepts and Taxonomy of Dependable and Secure Computing," IEEE TDSC 2001) splits "a bug" into a causal chain. A fault is the defect in the code: static, cheap to fix. An error is the deviated internal state an activated fault produces, invisible from outside. A failure is the delivered service deviating from the spec.

/* the fault: writes n+1 bytes into an n-byte destination */
void copy_name(char *dst, const char *src, size_t n) {
    for (size_t i = 0; i <= n; i++)   /* <= — off-by-one */
        dst[i] = src[i];
}
 FAULT                  ERROR                  FAILURE
 (code, dormant)        (deviated state)       (observed)

                      adjacent chunk's      "invalid next size (fast)",
                      size field:           10^7 cycles later, deep
                      0x31 -> 0x41          in malloc, no app frames
     |                  |                    ^
     | activation:      | propagation:       |
     | a 64-byte name   | chunk is freed,    |
     | finally arrives  | reused             |
     v                  v                    |
  (may take years)   (silent)            (the site you debug first)

Read it right to left: the failure site is three stages from the fault. malloc is not the culprit but the detector that caught the error ten minutes late — and that is what sanitizers automate, reporting errors at propagation time, before they become failures (ch05). The chain explains three pieces of folklore: rebooting "fixes" things because restart clears errors while the fault stays in the code; defensive checks are error-containment barriers; old code that "worked for years" never met its activation input.

Why late is expensive. Boehm's defect-cost escalation (Software Engineering Economics, 1981, IBM and TRW data; refreshed by Boehm & Basili 2001): a defect costing 1 unit at requirements time costs ~10 by implementation and ~100 after release, for large projects (small non-critical ones run ~5:1). The curve is exponential in phase because each phase stacks artifacts on the assumption — design decisions, calling code, tests, docs, deployed data — and a late fix invalidates them all. For the memory and state families the error has already propagated into persisted data, so field cost includes data repair, not just a recompile.

Two managed metrics make the iceberg measurable. Defect density (defects per KLOC): JPL's "Power of Ten" rules (Holzmann, 2006) exist so Class A flight code can hold ≤ 0.1 defects/KLOC, bought with static analysis plus review; typical delivered commercial code measures 1–5 defects/KLOC (Capers Jones's sampling — an order of magnitude, not a constant). Defect-removal efficiency (the iceberg ratio, found vs shipped): Jones and Bonsour (The Economics of Software Quality, 2011) measure ~85% of defects removed before release on average projects, >95% for the best teams combining inspections with testing. The average team ships one bug per six it finds; your users are the last test suite you own.

What insiders know

  • The 100:1 number gets misquoted constantly. Boehm & Basili (2001) is 100:1 for large projects, 5:1 for small non-critical ones; a universal "10x" is the folklore version.
  • glibc tcache leaves freed data mostly intact. On glibc ≥ 2.29 a tcache free clobbers only the first 16 user bytes (next + key); a use-after-free at offset ≥ 16 reads old, plausible data and passes. Make it loud: MALLOC_PERTURB_=170. Change reuse: GLIBC_TUNABLES=glibc.malloc.tcache_count=0 (glibc 2.35+ syntax).
  • Sanitizers perturb what they observe. ASan moves every allocation (redzones plus 1:8 shadow) and quarantines frees; TSan slows execution 5–15x, changing interleavings. "Does not reproduce under the sanitizer" is not evidence of absence.
  • A bug report without the optimization level is not reproducible. The same data race lost ~47% of 2,000,000 increments at -O0 and printed the correct total at -O2 (gcc 14.2, x86-64: one addq $0xf4240). Build flags are part of the program's identity, like the allocator.
  • gcov counts arcs, not paths. The lab's 5-branch function reports "12 branches" (10 from the ifs, 2 from main's usage guard). 100% branch coverage was 2/32 paths.
  • ~70% launched the rewrite wave. MSRC (Matt Miller, BlueHat 2019) and Chromium (2019) each measured ~70% of severe vulnerabilities as memory-safety bugs (module 01 ch21 has the receipts).

See it yourself

Both labs ran on Debian 13, gcc 14.2.0, glibc 2.41, x86-64, 2 cores. Your numbers will differ; that difference is section 4.

Lab 1 — count the paths, then watch the metric lie:

$ gcc --coverage -O0 discount.c -o discount   # = -fprofile-arcs -ftest-coverage
$ ./discount 70 1 1 1 1
discount=35
$ ./discount 30 0 0 0 0
discount=0
$ gcov -b discount.c
File 'discount.c'
Lines executed:100.00% of 13
Branches executed:100.00% of 12
Taken at least once:91.67% of 12
Calls executed:66.67% of 3

Two runs, 13/13 lines, every if taken both ways — yet only 2 of 32 paths. The one untaken arc (91.67%) is main's usage guard: the tool counts arcs, never paths. Now pay for the whole space:

$ rm -f discount.gcda && for i in $(seq 0 31); do
    ./discount $(( (i&1) ? 70 : 30 )) $(( (i>>1)&1 )) $(( (i>>2)&1 )) \
               $(( (i>>3)&1 )) $(( (i>>4)&1 )) > /dev/null; done
$ gcov -b discount.c     # same 91.67%, but all 32 paths now ran

Thirty-two launches to path-cover a 20-line function; each new branch doubles the bill.

Lab 2 — a Heisenbug you can schedule and unschedule:

$ gcc -O0 -pthread race.c -o race0 && gcc -O2 -pthread race.c -o race2

Same source, same machine, same day, three outcomes: at -O0 on two cores ~47% of increments are lost, a different number every run (timing is an input); at -O2 the compiler legally collapsed the racy loop into one addq (data race = UB, C11 §5.1.2.4); pinned to one core, 13/13 runs printed the correct total — the scheduler stopped supplying the losing interleaving. The fault (unsynchronized counter++) is present in every configuration; the failure is optional.

How to use this knowledge

  • Walk crashes backwards through the chain. The abort in free() is a failure; hunt the error (which byte, which chunk) and the fault (which write crossed a boundary). Never patch at the failure site.
  • Pick the detector from the family, not the symptom. Memory → ASan, concurrency → TSan, numeric UB → UBSan, state → invariant checks plus fault injection. The wrong sanitizer on a race proves nothing (ch05).
  • Reproduce by matching the invisible inputs. Allocator (LD_PRELOAD=libjemalloc.so.2, MALLOC_PERTURB_=170, glibc.malloc.tcache_count=0), build flags (-O0 vs -O2), core count (taskset), ASLR (setarch -R).
  • Defend review time with the curve. A fault caught in review is the 1-unit fix; post-release it is the 100-unit one plus incident response. That is the business case for review and CI in one number.

Answers
  1. The sentence defines only the behavior set. The bug lives between the spec (intended input → behavior mappings, mostly unwritten) and the behavior the program plus environment delivers; "what I wrote" pins the second and says nothing about the first. With the spec implicit, whether a divergence is a bug is an intent decision — a product call that, once written, makes the divergence measurable and testable.
  1. Fault: the defect in the code, static, cheap. Error: the deviated internal state an activated fault produces, invisible from outside. Failure: the delivered service deviating from the spec. Rebooting clears errors (state) while the fault (code) remains — reboot is error containment, not repair.
  1. (a) 2^7 = 128. (b) 128 × 1 ms = 0.128 s. (c) 24 h = 8.64 × 10^7 ms; need 2^B > 8.64 × 10^7, so B > log2(8.64 × 10^7) ≈ 26.36, hence B = 27. Check: 2^26 = 67,108,864 tests ≈ 18.6 h (fits); 2^27 = 134,217,728 ≈ 37.3 h (exceeds 24 h).
  1. (a) Placements of thread A's 6 blocks among 12 slots: C(12,6) = 924. (b) 924^3 ≈ 7.89 × 10^8, since each iteration interleaves independently. Formula: ((k1 + k2)! / (k1! · k2!))^iterations.
  1. Fault: the <= writing 65 bytes into a 64-byte buffer. Error: byte 65 corrupts the adjacent chunk's size field (0x31 → 0x41-style damage), silently. Failure: the abort in free(). The gap is activation plus propagation latency: the fault fires only when a 64-byte name arrives, and the corrupted chunk must be freed and reused before glibc's check trips — 10^7 cycles later. malloc is the detector, not the culprit; the fix belongs at the <=.
  1. A Heisenbug: a concurrency bug whose probability is set by invisible inputs — thread schedule, allocator state, core count, timing. (a) The debugger stops all threads on attach and at breakpoints, changing the interleaving distribution. (b) printf takes the stdout lock and allocates on first use (buffering), serializing timing and perturbing tcache state. Halving the rate with logging is a measurement effect, not a fix; the repair is synchronization.
  1. Chain: jemalloc's size classes and free-list policy differ from glibc's tcache → the same allocation sequence places the 64-byte object next to different neighbors → the 65th byte hits a size field on one allocator and padding on the other → the check in free() trips only where metadata was hit. On the dev laptop: LD_PRELOAD=libjemalloc.so.2 to match the allocator, MALLOC_PERTURB_=170 to surface latent use-after-free (then glibc.malloc.tcache_count=0, taskset). Reproduction = matching invisible inputs.
  1. (1) No runtime check: nothing in C/C++ verifies bounds, lifetime, or ownership at access time, so touching unowned bytes is expressible and unchecked; faults accumulate. (2) Silent propagation: memory errors corrupt state and surface as distant, severe failures (leaks, control-flow hijack). (3) Determinism given layout: memory faults fire on every execution of the path, so fuzzing finds them at scale while races hide behind rare interleavings — discovery is biased toward memory. (4) Convergence: numeric and parsing faults often end as memory corruption (an overflowed length feeds malloc → heap overflow).
